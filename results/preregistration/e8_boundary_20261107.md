# E8 — Boundary condition: complementary vs alternative relevant documents (pre-registered)

Written and hashed on 2026-11-07, **before** MuSiQue, 2WikiMultihopQA or DBpedia-Entity were downloaded, built or
scored. Only Hugging Face metadata was read: file lists and sizes, the 2Wiki parquet schema, and the field names of
one MuSiQue line, with no values. The pipeline (`scripts/run_boundary_pipeline.sh`) runs once and the result is
reported whatever it is.

## Why

E4 (`phase2_strengthening_20261107.md`) came out **inconclusive**. The split-half reference AUC′ was 0.750
[0.730, 0.769] pooled, but 0.522 [0.501, 0.559] without hotpotqa (a pre-declared secondary) and 0.53–0.60 on every
other fresh dataset, against 0.838 on hotpotqa. The explanation proposed **after** seeing that result:

> In most collections a query's relevant documents are **alternatives** (any duplicate question, any relevant paper),
> so which retriever wins depends on which one you look at. In multi-hop QA they are **complements** (each needed for
> the answer), and a retriever that handles the question tends to find all of them, so the winner is a property of
> the query.

Supporting pattern, also seen only after the fact: hotpotqa was also the only fresh dataset where the learned skip
router beat H1 (+0.0131), and where E2(c)'s best percentile AUC′ was highest (0.658, against 0.624 for scidocs + nq).
Because this explanation was derived from the data, it is tested here on new data.

## Data (fixed rules)

- **Complementary (multi-hop):** the two standard multi-hop QA benchmarks besides HotpotQA, using the
  most-downloaded raw release of each: **MuSiQue** (`dgslibisey/MuSiQue`, `musique_ans_v1.0_dev.jsonl`, all
  questions) and **2WikiMultihopQA** (`xanhho/2WikiMultihopQA`, `dev.parquet`, 3,000 questions sampled with seed
  42). Corpus = union of the questions' provided paragraphs (deduplicated); relevant = supporting paragraphs. The
  corpus therefore includes each question's built-in hard distractors.
- **Alternative (control):** **DBpedia-Entity** (`mteb/dbpedia`), the next unused BEIR dataset by the earlier
  size rule. Each relevant entity is an independent answer. All test queries; corpus = judged documents plus a
  seed-42 reservoir sample of distractors, up to 50,000 documents.
- Built by `scripts/build_boundary_datasets.py`. Pipeline as in E2–E7: BM25, e5-small-v2, top-100, min-max
  fusion, 5-fold CV, seed 42.

## Test (`scripts/compare_boundary.py`)

Split-half reference AUC′ exactly as in E4 (5 random halvings of each query's relevant documents; half-A dense −
BM25 margin → half-B binary winner), pooled within each group; bootstrap 2,000 resamples of whole queries within
each group.

- (a) complementary AUC′ ≥ 0.70 **and** its 95% CI low > 0.65;
- (b) alternative (DBpedia) AUC′ < 0.65;
- (c) difference (complementary − alternative): 95% CI low > 0.

**Accept** if (a), (b) and (c) all hold. **Reject** if the complementary AUC′ < 0.60 **or** the difference CI
high ≤ 0. **Inconclusive** otherwise.

**Secondary (no verdict):** router − H1 and router − hybrid at a 20% skip rate per group (predicted: router − H1 > 0
on the complementary group, as on hotpotqa); E2(c) best percentile AUC′ per group (predicted: higher on the
complementary group); the full `analyze_label_reliability.py` table.

**Prediction:** accepted. Main risks:
- MuSiQue and 2Wiki corpora are built from each question's own distractor paragraphs, which differ from
  hotpotqa's open corpus.
- 2Wiki "comparison" questions (two entities of the same type) may behave more like alternatives.
- DBpedia has only ~400 queries, so its CI will be wide.
